There is no best mesh protocol, only a better fit for a situation. This module turns everything so far into a
decision you can defend: name the inputs, say which evidence each one points to, and say what would change your
mind. The full side-by-side tables live on the [comparison page](../../comparison/); this lesson teaches how to use
them.

## Goals and prerequisites

You need the airtime counts from [Module 07](../07-reliability-capacity/), the security tables from
[Module 08](../08-privacy-security-rules/) and the community-first plan from [Module 10](../10-neighborhood-mesh/).

## Same hardware, different worlds

The two-node kit in Module 02 can run either firmware: the same boards have build targets for both. <Cite ids="HW-C11 HW-C04" />
That makes a fair comparison possible, because differences come from software. <Cite ids="HW-C07" /> It doesn't make
the two compatible:

- Even with identical frequency, bandwidth, spreading factor and coding rate, framing settings such as the sync word
  differ, and what one stock radio does with the other's frames is not established. <Cite ids="LW-C04" />
- Above the radio, the packet formats are different, so neither can read the other's messages natively. <Cite ids="LW-C02" />
- The apps talk to their nodes with different local protocols too. <Cite ids="LW-C03" />

So the first input to any decision is: **what are the people you want to reach already running?**

## What actually differs

| Dimension | Meshtastic 2.7.26 | MeshCore 1.18.0 |
|---|---|---|
| Who relays | Ordinary clients can relay; duplicate cancellation trims copies when relays hear each other <Cite ids="MT-C03" /> | Dedicated repeaters; companions don't by default <Cite ids="MC-004" /> |
| DM routing | Floods first; learns a per-hop next node; final retry floods again <Cite ids="MT-C10 MT-C11" /> | Floods first; learns a full stored path; a broken hop needs an explicit reset <Cite ids="MC-008 MC-011 MC-012" /> |
| Channel integrity | Channel AES-CTR has no authentication tag <Cite ids="MT-C17" /> | 2-byte truncated HMAC <Cite ids="MC-022" /> |
| DM crypto | X25519 + AES-256-CCM <Cite ids="MT-C18" /> | Identity-derived secret, AES-128, 2-byte MAC <Cite ids="MC-022" /> |
| Group history | None in core scope | Room server (operator can read) <Cite ids="MC-026" /> |
| Telemetry and app data | Many application ports (position, telemetry, traceroute and more) <Cite ids="CUR-C06" /> | Adverts with optional location; repeater stats over console <Cite ids="MC-031" /> |
| Automation | Python CLI and library; MQTT bridging <Cite ids="MT-C24 CUR-C10" /> | Companion protocol for apps; repeater console <Cite ids="MC-031" /> |
| Ecosystem | Official apps per platform; app and firmware versions must be checked, not assumed <Cite ids="MT-C25" /> | Firmware lineage and app distribution are separate questions after the 2026 split <Cite ids="MC-001 MC-003" /> |
| Security maintenance | First-party advisories with affected and fixed versions <Cite ids="MT-S29" /> | Fixes land in the latest release only <Cite ids="MC-032" /> |

## Seven scenarios

Each row gives the inputs that matter, a conditional recommendation and what would change it.

| Scenario | Key inputs | Recommendation | Would change if… |
|---|---|---|---|
| **Solo learner, no radios** | No hardware, wants concepts | Neither yet: do the simulations for both, then decide with the local check | A friend nearby already runs one |
| **Two radios, one pair of people** | Two nodes, direct range | Either. Run Module 03 and Module 05 on the same boards and compare | One person needs automation (lean Meshtastic CLI) or room history (lean MeshCore) |
| **Moving group** (hikers, event) | Nodes move, no fixed sites, short sessions | Meshtastic: any client can relay as the group spreads out, with no repeater to place | The area already has dense MeshCore repeaters along the route |
| **Established infrastructure** | A local community runs one protocol with coordinated relays | **Join what's there,** with their settings for your area <Cite ids="NTX-C01 NTX-C02" /> | Never, unless the community itself migrates |
| **Sparse rural link** | Few nodes, long gaps, someone can host a high site | MeshCore repeater at the high site fits planned links; Meshtastic `CLIENT` relays work if nodes are in place anyway | Nobody can maintain the high site |
| **Fixed relay backbone** | Several permanent sites, an operator, maintenance budget | MeshCore's dedicated repeaters and stored paths suit planned backbones; Meshtastic `ROUTER` roles also exist and need coordination | The users on the edges already run Meshtastic |
| **Privacy-sensitive use** | Content and identity matter | Neither is a secure messenger. Prefer DMs over channels on both; on Meshtastic, channel messages aren't integrity-protected. Minimize position and bridges | A threat model shows metadata (who, when, where) is the real risk: then reconsider using radio at all |

## Worked example: a sparse rural link

**Scenario.** Two farmhouses 6 km apart can't hear each other. A grain-elevator owner offers a high site that can
see both, with mains power, and one farmer will maintain it. Nobody nearby runs either protocol.

1. **Existing users?** None, so step 1 of the decision flow doesn't decide it.
2. **Fixed relay possible?** Yes: one permitted, powered, maintained high site.
3. **Evidence for each option.**
   - MeshCore: a repeater at the elevator; both farmhouses run companions. The first DM floods through the repeater,
     then each side uses its stored path `[repeater]`. Two transmissions per message plus a direct ACK. <Cite ids="MC-008 MC-009" />
   - Meshtastic: a `CLIENT` (or, by agreement, `ROUTER_LATE`) at the elevator. Two transmissions per broadcast with
     hop limit 1; a DM learns a next hop. <Cite ids="MT-C10" />
4. **Tie-breakers.** Do the farmers want automated sensor logs? That favors Meshtastic's telemetry and CLI. <Cite ids="CUR-C06 MT-C24" />
   Do they want messages waiting for whoever comes in from the field? A MeshCore room server at the elevator does
   that, with the farmer as a trusted operator. <Cite ids="MC-026" />
5. **Recommendation.** Either works on this topology. With no logging need and a wish for stored messages: MeshCore
   with a repeater and a room server. With logging: Meshtastic.
6. **What would change it.** A third house appearing that only one farmhouse can hear: a Meshtastic client there
   relays with no extra setup, while on MeshCore a companion there forwards nothing until someone deploys or
   reconfigures it as a repeater. <Cite ids="MC-004" />

## Your turn: recommend for a scenario

A volunteer search team of 8 wants to message between a base and moving teams in hilly woodland. One member can
place a relay on a ridge for a weekend. The local community runs Meshtastic, but nobody uses it near this forest.
They also want the base laptop to log positions automatically.

Make a recommendation, name the three inputs that decided it, and say what would change it.

<details>
<summary>Suggested answer</summary>

Meshtastic. Inputs: (1) the local community runs it, so team members may already have nodes and know the app;
(2) moving teams benefit from any client relaying without planning; (3) the base wants automated position logging,
which the Python CLI and library can support. <Cite ids="MT-C24 CUR-C06" /> The ridge relay is a coordinated
infrastructure role for the weekend only. What would change it: a MeshCore repeater network already covering the
forest, or no need for position logging. Either way this is a supplementary channel with variable delivery, not a
replacement for the team's primary communications.
</details>

## Knowledge check

<details>
<summary>1. Your neighbor runs MeshCore on the same board and the same frequency as your Meshtastic node. Can you message each other?</summary>

No. Different packet formats and framing; matching RF settings don't change that. <Cite ids="LW-C02 LW-C04" />
</details>

<details>
<summary>2. Why is "join what's there" the strongest input?</summary>

Nodes only help each other if they run the same protocol and settings. A technically better choice that nobody
nearby uses gives you a two-node network.
</details>

<details>
<summary>3. Someone says MeshCore is "more reliable" because its routes are stored. What's the trade?</summary>

A stored path is efficient while it's right. When a hop breaks, a different reachable repeater doesn't step in;
recovery needs a reset and a new flood. <Cite ids="MC-011 MC-012" />
</details>

<details>
<summary>4. A group needs messages kept for members who were off air. What fits, and at what cost?</summary>

A MeshCore room server stores recent posts, but its operator can read them and history is a bounded queue. <Cite ids="MC-026" />
</details>

<details>
<summary>Deeper dive: comparing fairly on hardware</summary>

Use two identical boards, the same antennas and placements, the same RF settings where both protocols allow them,
and the same message schedule. Reflash both nodes between runs; reflashing erases identities, so re-exchange contacts
each time. Report each protocol's PDR with sample size, and label differences in frame size and protocol behavior,
not just the totals. <Cite ids="HW-C07" />
</details>
